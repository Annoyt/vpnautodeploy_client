# Несколько каналов связи в NekoVPN (E37) — предположение

Статус: **черновик, 2026-10-25.** Владелец попросил посмотреть, как встроить в
клиент идеи [net-merge](https://github.com/rohit267/net-merge),
[Plexo](https://github.com/anmolkapil/plexo) и
[Speedy](https://github.com/RezaRafia/Speedy). Как этим пользоваться, решим
позже. Ниже описано, что эти проекты делают на самом деле, три режима, которые
из них можно получить, и куда каждый режим встаёт в коде форка.

## 1. Что делают эти проекты

Все три раскладывают **разные соединения по разным сетям**. Одно соединение
целиком идёт по одной сети, одни и те же пакеты по двум сетям никто из них не
отправляет. То есть это «два разных подключения», а не дупликация.

| Проект | Как устроен | Что из него берём |
|---|---|---|
| net-merge (Go, MIT) | Системный TUN с gVisor; каждое новое соединение набирается с адаптера, у которого меньше всего потоков на единицу веса. Сервера нет. Для Android есть отдельная бета `net-merge/android`: `requestNetwork` для каждой сети и привязка сокета к сети | Планировщик и Android-часть: как держать мобильную сеть поднятой рядом с Wi-Fi и привязывать сокет к сети |
| Plexo (TypeScript/Electron, MIT) | Менеджер загрузок: режет один файл на куски (HTTP Range) и качает их через сокеты, привязанные к разным сетям | Только идею: одну закачку ускоряет лишь тот, кто сам режет её на части. Для VPN-клиента это недоступно, приложения качают как умеют |
| Speedy (TypeScript/Electron) | Локальный SOCKS5. Каждое новое соединение уходит на следующий интерфейс по взвешенному кругу (веса задаёт пользователь, «чтобы управлять расходами») | Идею долей на каждую сеть в интерфейсе. Код не годится: исходящий сокет к сети не привязывается, файла лицензии в репозитории нет (MIT заявлен только в README) |

Что из этого следует, проверено по документации Android и ядрам (подробности в
отчёте исследования от 2026-10-24):

- **Две SIM одновременно — нельзя.** Android держит одно подключение для
  данных на всё устройство, интернет со второй SIM приложению не дают.
- **Wi-Fi + мобильная одновременно — можно**, так же как Ethernet или
  USB-модем: `requestNetwork` держит мобильную сеть поднятой, сокет
  привязывается к нужной сети. Раздача с другого телефона по Wi-Fi или кабелю
  для телефона-получателя — та же вторая сеть.
- **Одну закачку быстрее не сделать** без агрегатора на сервере: MPTCP в
  ядрах Android (GKI) выключен, а свой агрегатор — это новый протокол и новые
  признаки для DPI.

## 2. Три режима

Ниже под «сетью» понимается Wi-Fi, мобильная сеть, Ethernet или USB-модем.

### 2.1 Резерв (failover) — размер S

- **Что даёт.** Мобильная сеть остаётся поднятой рядом с Wi-Fi. Как только
  путь до наших серверов через Wi-Fi перестаёт отвечать (проверки по каждой
  сети отдельно), новые соединения сразу идут через мобильную, не дожидаясь,
  пока Android сам признает Wi-Fi плохим. Типичный случай: «Wi-Fi есть, а
  интернета нет» в кафе, гостинице, метро.
- **Цена.** Мобильная сеть держит радиомодуль включённым: батарея. Трафик по
  ней идёт только при отказе Wi-Fi.
- **Сервер.** Ничего нового.

### 2.2 Распределение («два разных подключения») — размер M

- **Что даёт.** Каждое новое соединение до наших серверов уходит в ту сеть,
  где сейчас меньше нагрузка с учётом её скорости, как в net-merge и Speedy.
  Быстрее работает всё, что открывает много соединений сразу: браузер,
  магазин приложений, торренты, многопоточные загрузчики. Отказ одной сети
  переживается сам собой.
- **Ограничения.**
  - Одна закачка в одно соединение быстрее не станет.
  - Hy2 возит весь трафик в одном QUIC-соединении, поэтому целиком окажется в
    одной сети. Разложить можно протоколы, где каждое соединение приложения —
    своё соединение до сервера: Reality, ShadowTLS, CDN-ws.
- **Цена.** Мобильный трафик тратится и дома. Нужны доли на каждую сеть, как
  в Speedy, и предупреждение о расходе.
- **Сервер.** Ничего нового, но надо проверить две вещи:
  - не банит ли 3x-ui клиента с двух адресов: у клиента `limitIp=1`, и если на
    exit включён бан по IP через fail2ban, второй адрес попадёт под него;
  - телеметрию по операторам (R6, панель «Клиенты по операторам»): один
    клиент окажется в двух ASN сразу.

### 2.3 Дупликация — размер L, только UDP/QUIC

- **Что даёт.** Одни и те же пакеты идут по двум сетям сразу, доходит тот,
  что быстрее. Потери и задержки одной сети перестают быть заметны: для
  звонков и игр это надёжнее любого переключения. Скорость не растёт, трафик
  удваивается.
- **Почему только UDP/QUIC.** Получатель QUIC (Hy2) сам отбрасывает
  повторный пакет по его номеру, поэтому копии ничего не ломают. TCP-протоколы
  так не продублировать.
- **Сервер.** Нужен ретранслятор UDP на entry, по образцу
  [engarde](https://github.com/porech/engarde) (дупликация для WireGuard):
  - от клиента: каждая копия с любой сети отправляется дальше на hysteria,
    лишние QUIC выбросит сам;
  - к клиенту: каждый пакет hysteria отправляется на все живые адреса
    клиента.

  Для hysteria адрес клиента не меняется, это всегда ретранслятор, так что
  миграция соединения QUIC не возникает.
- **Риски.**
  - Новый UDP-порт и новый рисунок трафика — новые признаки для DPI. Нужна
    обфускация уровня salamander.
  - Мобильные сети режут UDP раньше всего (AGENTS.md сервера, §25, §30).
  - Удвоенный расход мобильного трафика.

## 3. Два устройства — два оператора («меш»)

Вопрос владельца (2026-10-27): собрать трафик с двух устройств в одно. Два
телефона с SIM разных операторов — это два независимых выхода в интернет.
Один Android две SIM одновременно не использует (раздел 1), а два телефона
используют. Технически это те же режимы из раздела 2. Отличие одно: вторая
«сеть» — это соседнее устройство.

Важно, что под «собрать» понимать:
- **Сумма для многих соединений** (браузер, магазин приложений, торренты,
  многопоточные загрузки): работает, это распределение (2.2).
- **Одна закачка быстрее любого из каналов**: нет. Нужен агрегатор на
  сервере, который собирает один поток из кусков, пришедших разными путями
  (MPTCP, Speedify, OpenMPTCProuter). Для нас это размер XL и новые признаки
  для DPI (раздел 1).
- **Связь, которая не рвётся, когда у одного оператора проблемы**:
  работает, это резерв (2.1) и дупликация для звонков (2.3). Это, пожалуй,
  главная польза для нас. Блокировки и белые списки у операторов разные: где
  МТС режет, МегаФон может пропускать, и наоборот.

### 3.1 Точка доступа + режимы раздела 2 (без приложения на втором телефоне)

- **Как устроено.**
  - Телефон Б включает точку доступа; телефон А подключается к ней по Wi-Fi
    и держит свою мобильную сеть (`requestNetwork(CELLULAR)`).
  - У А две сети: Wi-Fi (оператор Б) и своя мобильная (оператор А).
  - NekoVPN на А раскладывает по ним соединения (2.2), держит резерв (2.1)
    или дублирует звонки (2.3).
  - USB-модем и кабель от второго телефона — то же самое, как Ethernet.
- **Плюсы.** На Б ничего ставить не нужно; это самый дешёвый путь, и вся
  работа — на А.
- **Минусы.** Домашний Wi-Fi на А в это время недоступен: телефон держит
  одну Wi-Fi-сеть. Тратятся трафик и батарея Б.

### 3.2 Ретранслятор на втором телефоне (оба на одном Wi-Fi или в одной локальной сети)

- **Как устроено.**
  - На Б включён NekoVPN в режиме «помощник». Он принимает соединения А по
    локальной сети и отправляет их к нашим серверам через **свою** мобильную
    сеть: сокет привязан к сети Б, как в разделе 4.
  - А получает третий путь: свой Wi-Fi, своя мобильная и мобильная Б через
    ретранслятор.
  - Ретранслируется уже **зашифрованный** туннель до нашего сервера (как в
    E30): Б не видит, куда ходит А.
- **Почти всё уже есть в mihomo и FlClash.**
  - Входящий порт `mixed` 7890 с «Разрешить LAN». Это наш `/share` (E29),
    только нужна авторизация.
  - Цепочка `dialer-proxy`: в профиле А у каждого сервера появляется копия
    «через Б», которая набирает соединение через SOCKS5 на адрес Б.
  - Группа `load-balance` над прямыми и «через Б» копиями. В профиле Б наши
    серверы идут `DIRECT`, а не через его же туннель, иначе выйдет туннель в
    туннеле.
- **Что нужно добавить.**
  - Сопряжение одним QR: адрес Б, порт, одноразовый токен. Обнаружение через
    mDNS — как задумано в E30.
  - На Б — привязка ретранслируемых соединений к мобильной сети, а не к
    общему Wi-Fi.
  - Профиль: копии серверов «через Б». Их можно генерировать в приложении
    или на сервере, по метке сопряжения.
- **Ограничения.**
  - iPhone в фоне ретранслятором быть не может (E32).
  - Обоим телефонам нужен постоянно работающий NekoVPN.
  - Без авторизации на порту в ретранслятор может войти любой в этой сети.

### 3.3 Несколько устройств вскладчину (настоящий меш)

Каждый телефон и отдаёт свой канал другим, и пользуется чужими. Это 3.2,
обобщённое на N устройств: учёт, кто сколько отдал, честное деление,
выход устройств из сети. Имеет смысл только после того, как 3.2 покажет
пользу на практике. Отдельный проект.

### 3.4 На сервере

- **3.1 и 3.2** — ничего нового, кроме уже упомянутых проверок. У клиента
  `limitIp=1`: соединения одного пользователя придут с двух операторов, и
  бан по IP в 3x-ui, если он включён, их отрежет. Телеметрия по операторам
  (R6, панель клиентов) увидит одного клиента в двух ASN.
- **Дупликация звонков** через меш — тот же ретранслятор UDP на entry, что и
  в 2.3.
- **Сборка одного потока** — только свой агрегатор (XL).

## 4. Куда это встаёт в форке

Всё держится на одном месте: каждый исходящий сокет ядра проходит через
защиту от петли в VPN, и там же его можно привязать к выбранной сети.

| Место | Сейчас | Что добавить |
|---|---|---|
| `core/lib.go`, `installHooks` → `dialer.DefaultSocketHook` | Для каждого сокета ядра зовёт `handleProtect(fd)`; знает `network` (tcp/udp) и адрес сервера | Передавать `network` и адрес дальше, чтобы планировщик видел, что это за соединение (TCP к Reality, UDP к Hy2) |
| `core/mobile/mobile.go`, `TunHandler.Protect(fd)` | Мост gomobile в Kotlin | Тот же вызов с адресом и типом соединения |
| `VpnService.kt`, `protect = this::protect` | `VpnService.protect(fd)` привязывает сокет к сети по умолчанию | После `protect` — `Network.bindSocket(fd)` для сети, которую выбрал планировщик; `setUnderlyingNetworks` со всеми используемыми сетями, чтобы Android верно считал трафик и платные сети |
| `NetworkObserver.kt` | Следит за сетями, выбирает одну по приоритету (Wi-Fi → Ethernet → USB → мобильная) для DNS | При включённом режиме держать мобильную сеть через `requestNetwork(TRANSPORT_CELLULAR)`; хранить по каждой сети задержку, скорость и последнюю проверку |
| Планировщик (новый, `core/neko/` или Kotlin) | — | Резерв: первая живая сеть по приоритету. Распределение: минимум (потоки + 1) / вес, соединение не переезжает между сетями. Дупликация: UDP к ретранслятору — во все сети |
| Настройки (Flutter) | — | «Несколько сетей»: выкл / резерв / распределение / дублирование для звонков; доли сетей; предупреждение о мобильном трафике и батарее |
| Удалённые настройки (E14) | — | Сервер может выключить режим или задать значения по умолчанию, если режим вредит в какой-то сети |

Режим шлюза (E30) — обратная задача: телефон раздаёт свой туннель соседям.
С этим документом его роднит только привязка сокетов к сетям.

## 5. Предлагаемый порядок

1. **Сначала замер.** Тест скорости в приложении по каждой сети отдельно.
   Если потолок — наш entry или exit, а не связь пользователя, ни один режим
   скорости не прибавит.
2. **Резерв (S)** — самая частая польза при минимальной цене.
3. **Распределение (M)** — за переключателем, по умолчанию выключено, с
   долями сетей.
4. **Дупликация (L)** — отдельным проектом и только если звонкам или играм
   не хватит резерва.
5. **Меш.** Сначала 3.1 (точка доступа): он выходит из пунктов 2–3 почти
   даром. Потом, если будет спрос, ретранслятор 3.2 (M–L). 3.3 и сборка
   одного потока — только по отдельному решению.

## 6. Что решить владельцу

- Какой режим нужен первым и для кого: все, платные или по запросу.
- Тратить ли мобильный трафик, когда есть Wi-Fi (распределение и
  дупликация), и включать ли что-то по умолчанию.
- Нужна ли дупликация для звонков: это единственный режим, которому нужен
  новый сервис на entry.
- Меш: достаточно ли точки доступа (3.1), или нужен режим «помощник» (3.2) —
  второй телефон с NekoVPN, сопряжение по QR.
